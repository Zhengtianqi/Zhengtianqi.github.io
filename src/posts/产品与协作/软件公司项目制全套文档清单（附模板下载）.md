# 软件公司（项目制）全套文档清单：从投标到验收，43 份模板直接下载

项目制软件公司有个很典型的循环：投标时临时翻硬盘找资质和业绩，开工时靠一份合同和几段微信聊天记录，开发到一半客户说「这个不是应该包含吗」，验收时才发现没有一份双方签字的需求基线，最后回款卡在「验收报告没盖章」上。

人少、项目杂、偶尔才投一次标，恰恰是最需要把文档固化的团队——因为没有专职 PMO，任何一次人员变动都会把上下文带走。

这篇文章给出一套**能直接落地的最小可用文档全集**：按项目生命周期分成 6 组共 43 份，每一份都是可编辑的 Word / Excel 模板，不是空壳，含章节骨架、表头字段、示例行和填写说明，文末可以直接点击下载。

## 一、先说结论：文档不是越多越好，要挂在「决策」和「钱」上

很多公司一提规范化就买一套几十上百份的体系文件，最后没人填，全成了摆设。项目制公司判断一份文档要不要存在，只看两个问题：

1. **它是不是某个决策的依据？** 比如立项申请书决定给不给资源，需求确认书决定开发能不能开工，验收报告决定能不能收钱。
2. **出问题时要不要靠它追溯？** 比如变更单、会议纪要、交付签收单，平时没人看，争议时是唯一证据。

两个都答「否」的文档，直接删掉。下面这套清单就是按这个标准筛过的：过程记录类压缩到最少，把篇幅留给了**投标、范围基线、变更、验收、回款**这几处真正会出事的地方。

  │  D 开发测试变更  排期、周报、用例、缺陷、变更单               │
  │        ↓                                                   │

  │        ↓                                                   │

## 五、把文档绑到付款节点上，才会真的有人填

纯靠自觉的文档管理一定会失效。有效做法是：把每份文档变成流程里的**门禁**——上一阶段该签的字没签，下一阶段不启动；某个付款节点对应的文档没归档，财务不发起流程。

| 付款 / 里程碑节点 | 必须归档的文档 | 缺失的后果 |
| :--- | :--- | :--- |
| 合同生效 / 预付款 | 合同、B01 立项申请书、B02 合同评审记录 | 内部没有预算与人力基线，毛利事后才算得清 |
| 需求确认款 | C02 SRS、C03 需求确认书 | 范围没有基线，后续变更无法计价 |
| 上线 / 初验款 | D06 测试报告、E02 上线检查清单、E05 交付签收单 | 「上线了但没人承认」，试运行起算说不清 |
| 终验款 | E06 验收报告、C04 需求跟踪矩阵、E03 用户手册 | 验收结论模糊，尾款被无限期挂起 |
| 质保金退还 | F03 运维交接单、F04 满意度调查、F05 归档清单 | 质保期起算与责任边界扯不清 |

把这张表贴到项目看板上，比反复强调「大家记得写文档」有用得多。

## 六、落地三步

**第一步：统一命名和版本。** 用 F06 那套规则——`项目代号_文档编号_文档名称_V版本`，目录按 A–F 分组。所有项目目录长得一样，新人接手、投标找材料、结项归档都不用问人。Word 模板的页眉里 `【公司名称】` 替换一次即可全公司复用。

**第二步：设卡点，不搞事后补文档。** 需求确认书没签字不排开发计划；变更单没批不做实现；上线检查清单有不通过项不放行；验收报告没盖章不算结项。文档在流程里产生，才是活的。

**第三步：结项归档，反哺投标。** 用 F05 在一个月内收齐，把验收报告、合同扫描件同步登记进 F08 资质与业绩台账，投标时直接取用。A07 的复盘结论再回过头修正报价模型和工时估算系数——这套体系跑两轮之后，报价会明显变准。

## 八、几个常见疑问

**Q：小团队真的需要这么多文档吗？**
按第四节的 10 份起步就够。文档的价值不在数量，在于关键节点有没有留下一份双方认账的东西。哪怕一页纸的会议纪要，只要写清结论、责任人和期限，也比三段微信强。

**Q：客户提供了自己的模板怎么办？**
以客户模板为外壳交付，用本套表格做内部核对：尤其是 C04 RTM 和 E05 交付清单，确保客户模板里没有悄悄漏掉合同约定的交付物。

**Q：不是敏捷开发吗，还写这么多文档？**
敏捷省的是「为了流程而流程」的中间产物，省不掉范围基线、变更记录和验收凭据。这三张纸恰恰是让迭代能快速推进的前提——边界清楚，才敢小步快跑。

**Q：投标不频繁，A 组会不会白做？**
A 组里真正需要平时维护的只有 A06 报价模型和 F08 资质业绩台账；A01–A03、A07 是空表，用的时候再填。成本很低，但能避免「公告来了才发现证书过期」。
