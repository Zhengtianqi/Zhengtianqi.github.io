# AI漫剧系统设计开发思路

> 本文是一份 AI 漫剧系统的完整技术方案：从问题定义、架构设计、核心模块、数据流、领域模型，一直写到部署与运维。
> 目标读者是准备从零搭建或改造漫剧生产系统的研发与架构同学，读完可以直接拆任务开工。

---

## 一、先把问题定义清楚

### 1.1 什么是 AI 漫剧

AI 漫剧指以漫画 / 动漫视觉语言呈现的竖屏动态短剧：人物与场景由生成模型产出，靠"有限动画 + 镜头运动 + 配音旁白"承载叙事，单集 1–3 分钟，通常 60–120 个镜头，每镜 1.5–4 秒。

它和几个相邻形态经常被混为一谈，先把边界划清：

| 形态 | 画面来源 | 镜头量 | 核心成本 | 交付周期 |
|------|---------|--------|---------|---------|
| 真人短剧 | 实拍 | 80–150 | 演员、场地、导演 | 周级 |
| 传统二维动画 | 手绘 / 逐帧 | 200+ | 原画师人力 | 月级 |
| 条漫 | 静态分格 | 0 | 画师人力 | 天级 |
| **AI 漫剧** | **生成模型 + 有限动画** | **60–120** | **算力 + 审片人力** | **天级** |

关键差异在于：AI 漫剧不是"把短剧加个动漫滤镜"，而是**用分镜的密度换取单张画面的精致度**。观众接受"人物只眨眼、头发轻微飘动"，但不接受"人物每 2 秒换一张脸"。

### 1.2 一条成片的真实链路

系统采用 12 个阶段（S0–S11）：

| 阶段 | 名称 | 输入 | 输出 | 是否人工 |
|------|------|------|------|---------|
| S0 | 立项 | IP / 题材 / 画风 / 预算 | 项目卡 | 是 |
| S1 | 文本改编 | 原文 / 大纲 | 分集大纲 | 是 |
| S2 | 剧本 | 分集大纲 | 分场剧本（含对白） | 是 |
| S3 | 声音预演 | 剧本对白 | 配音 + 时长表 | 半自动 |
| S4 | 资产 | 角色 / 场景 / 道具设定 | 角色卡 + 风格卡 + 参考图 | 是 |
| S5 | 分镜 | 剧本 + 时长表 | 镜头表（景别/运镜/时长） | 是 |
| S6 | 静帧 | 镜头表 + 资产 | 关键帧图 | 是（审图） |
| S7 | 图生视频 | 通过的静帧 | 分镜视频 | 是（审片） |
| S8 | 视频质检 | 分镜视频 | 质检报告 + 重生成结论 | 半自动 |
| S9 | 音频合成 | 配音 + BGM + 音效 | 混音轨 | 自动 |
| S10 | 剪辑拼装 | 视频 + 音轨 + 字幕 | 整集成片 | 自动 |
| S11 | 审片交付 | 成片 | 多规格导出 + 归档 | 是 |

> **为什么把 S3 声音预演放在 S5 分镜之前？**
> 配音时长是分镜时长的唯一可信时钟。先写分镜再配音，几乎必然出现"画面演完了台词还没说完"或"台词完了画面空转"。先音后画，把每句对白实测时长量出来再切镜头，返工率会明显下降。

### 1.3 三个必须提前破除的误区

**误区一：一键成片。**

一次性丢一段小说进去直接出一集成片，在 30 秒演示里能跑通，在 3 分钟正片里一定崩。误差按镜头累积：单镜可接受率 85%，60 个镜头全部可用概率只剩 0.85^60 ≈ 0.6%。系统必须设计成"逐镜生成 + 逐镜人审 + 局部重生成"。

**误区二：模型决定论。**

当基线模型达到可用水平后，瓶颈在管线：提示词是否结构化、角色是否锁定、首帧是否继承、失败能否重试、参数是否留痕。同一套模型，管线做得好与差，一次通过率能差一倍以上。

**误区三：只做 UI。**

工作台界面最好做，也最像 Demo。真正吃工期的是任务队列、显存预检、失败语义、成本核算、血缘复现、权限隔离。

### 1.4 设计目标与非目标

| 类别 | 内容 |
|------|------|
| 目标 | 单集可交付；同参数可复现；单集成本可核算；多人多项目并行；算力可水平扩展 |
| 非目标 | 全自动无人工；影视级画质；实时生成；替代专业动画中期制作 |

把非目标写进设计文档很重要——它会挡住后面无数的"能不能再加个功能"。

## 二、总体架构设计

### 2.1 逻辑视图：六层架构

```
┌──────────────────────────────────────────────────────────────┐
│ 接入层    Web 工作台 / OpenAPI / Webhook 回调                  │
├──────────────────────────────────────────────────────────────┤
│ 应用层    项目 · 剧本 · 分镜 · 资产 · 审片 · 权限 · 计费        │
├──────────────────────────────────────────────────────────────┤
│ 编排层    Pipeline Engine：S0–S11 状态机 · 阶段门禁 · 补偿      │
├──────────────────────────────────────────────────────────────┤
│ 能力层    模型网关 · 提示词编译器 · 一致性服务 · 质检 · 合成     │
├──────────────────────────────────────────────────────────────┤
│ 算力层    ComfyUI 集群 · TTS · LLM · 转码 Worker               │
├──────────────────────────────────────────────────────────────┤
│ 数据层    PostgreSQL · Redis · 对象存储 · 向量库               │
└──────────────────────────────────────────────────────────────┘
```

| 层 | 职责 | 不应该做的事 |
|----|------|-------------|
| 接入层 | 鉴权、限流、参数校验、协议转换 | 写业务规则 |
| 应用层 | 领域对象增删改查、权限判定、计费 | 直接调 GPU |
| 编排层 | 阶段推进、门禁、重试与补偿 | 关心提示词内容 |
| 能力层 | 提示词编译、模型路由、一致性、质检 | 感知项目结构 |
| 算力层 | 执行推理、产出文件 | 感知业务状态 |
| 数据层 | 持久化、缓存、对象存储 | 承载业务逻辑 |

核心约束只有一条：**依赖方向单向向下**。应用层不知道 ComfyUI 的存在，编排层不知道前端的存在。这条约束决定了后面换模型、换队列、换存储时要不要重写。

### 2.2 运行时视图：进程与部署单元

```
                     ┌─────────────┐
   浏览器 / 开放平台 ─►│ CDN + 静态页 │
                     └──────┬──────┘
                            │ HTTPS
                     ┌──────▼───────────────┐
                     │ API 服务（N 副本）    │ 无状态
                     └──┬────────┬────────┬──┘
              ┌─────────┘        │        └──────────┐
       ┌──────▼─────┐    ┌───────▼──────┐   ┌───────▼──────┐
       │ PostgreSQL │    │    Redis     │   │  MinIO / S3  │
       └──────┬─────┘    └───────┬──────┘   └──────▲───────┘
              │                  │                 │
       ┌──────▼──────────────────▼──────┐          │
       │ Worker-CPU 池（质检/转码/合成） │──────────┘
       └──────────────┬─────────────────┘
                      │ 生成任务
       ┌──────────────▼─────────────────┐
       │ Worker-GPU 池（ComfyUI 适配器）  │
       └──────────────┬─────────────────┘
                      │ HTTP / WebSocket
       ┌──────────────▼───────┐  ┌─────────┐  ┌─────────┐
       │ ComfyUI 实例 × N     │  │ TTS 服务 │  │ LLM 服务 │
```

| 部署单元 | 状态 | 副本 | 资源特征 | 说明 |
|---------|------|------|---------|------|
| web | 无状态 | 任意 | 极低 | 静态资源，CDN 分发 |
| api | 无状态 | ≥2 | CPU 中等 | SSE 长连接需注意连接数 |
| worker-cpu | 无状态 | 按任务量 | CPU 高、IO 高 | 质检、转码、拼装 |
| worker-gpu | 无状态 | 按 GPU 数 | 1 卡 1 副本 | 只做协议适配，不跑模型 |
| comfyui | 有状态（模型缓存） | 1 卡 1 实例 | 显存独占 | 需健康检查与显存预检 |
| postgres | 有状态 | 主从 | 磁盘 IO | 任务表是热点 |
| redis | 有状态 | 主从 / 哨兵 | 内存 | 进度推送、锁、限流 |
| minio | 有状态 | 多节点 | 大容量磁盘 | 存放全部产物 |

### 2.3 部署视图：三种形态与演进路径

| 形态 | 适用 | 拓扑 | 单集耗时 | 演进信号 |
|------|------|------|---------|---------|
| 单机版 | 个人 / 验证 | 一台带 GPU 的机器，Compose 起全部 | 1–2 天 | 需要多人同时用 |
| 工作室版 | 3–10 人 | API 机 + 1–4 台 GPU 节点 + 独立存储 | 半天–1 天 | GPU 排队超过 2 小时 |
| 集群版 | 10 人以上 / 多项目 | K8s + GPU 节点池 + 对象存储 + 监控栈 | 数小时 | 需要跨地域 / 多租户 |

**不要跳级。** 单机版能跑通再上工作室版，工作室版稳定后再上 K8s。过早集群化会让每次调试都要跨容器排查，收益为负。

### 2.4 五个核心设计决策

**决策一：模块化单体起步，不做微服务。**

漫剧系统的瓶颈在 GPU 和人工，不在 Web QPS。起步阶段一个 FastAPI 进程 + 一个 Worker 进程足够。但代码层面要守住模块边界（应用 / 编排 / 能力 / 适配），等真的需要按算力池拆分时再动手。

**决策二：编排与执行分离。**

编排层只决定"下一步做什么"，执行层只负责"把一个任务做完"。这样重试、暂停、改参数重跑都不需要改生成逻辑。

**决策三：模型网关统一收口。**

所有生成调用（文本 / 图像 / 视频 / TTS）都经过统一网关，业务层只传"步骤 + 提示词 + 参数"，由网关决定路由到本地 GPU 池、自建集群还是商用 API。配额、熔断、降级、成本核算只在一处实现。

**决策四：资产即代码。**

角色卡、风格卡、提示词模板、分镜表全部版本化为 YAML / JSON，存库也存 Git。既有 diff 能力，也支持回滚与一键复现。

**决策五：产物只走对象存储。**

图片、视频、音频一律不落数据库、不走 API 中转，客户端用签名 URL 直传直取。数据库只存 URI 与元数据，否则一集几十 GB 的产物会把数据库和带宽一起拖垮。

### 2.5 技术选型

| 层 | 选型 | 理由 |
|----|------|------|
| 后端 | Python 3.12 + FastAPI | 与推理生态同语言，异步原生 |
| 编排 | 自研轻量状态机（起步）/ Temporal（规模化） | 阶段少、状态明确，自研可控 |
| 队列 | PostgreSQL `FOR UPDATE SKIP LOCKED` | 起步不引额外组件，语义足够 |
| 数据库 | PostgreSQL 16 | JSONB 存参数与工作流快照 |
| 缓存 | Redis | 进度推送、分布式锁、限流 |
| 对象存储 | MinIO / S3 | 签名 URL、生命周期、版本化 |
| 推理 | ComfyUI（图像 / 视频）+ Ollama 或云端 LLM | 工作流可版本化，节点生态成熟 |
| 音频 | TTS 服务 + FFmpeg | 混音、响度、字幕烧制一站式 |
| 前端 | Vue 3 / React + SSE | 工作台重交互，进度用 SSE 而非轮询 |
| 观测 | OpenTelemetry + Prometheus + Grafana | 任务链路可追踪 |
| 部署 | Docker Compose → Kubernetes | 按规模平滑演进 |

## 三、核心模块设计

### 3.1 模块总览

```
┌─────────────────────────────────────────────────────────────┐
│  身份权限   │  项目内容   │  编排引擎   │  模型网关   │  存储  │
└──────┬──────┴──────┬──────┴──────┬──────┴──────┬──────┴───┬───┘
       │             │             │             │          │
┌──────▼──────┐┌─────▼──────┐┌─────▼──────┐┌─────▼─────┐┌───▼───┐
│ 提示词编译器 ││ 一致性服务  ││  质检模块  ││ 音频合成  ││ 渲染  │
└─────────────┘└────────────┘└────────────┘└───────────┘└───────┘
```

| 模块 | 职责 | 对外接口 | 依赖 |
|------|------|---------|------|
| 身份权限 | 登录、RBAC、项目隔离 | `/api/auth/*` | PG |
| 项目内容 | 项目 / 剧本 / 分镜 / 资产 CRUD | `/api/projects/*` | PG、MinIO |
| 编排引擎 | 状态机、门禁、重试、补偿 | 内部 API + 事件 | PG、队列 |
| 模型网关 | 路由、配额、熔断、成本 | `/internal/generate` | Worker、Redis |
| 提示词编译器 | 分层合成、冲突消解、负面词合并 | 纯函数库 | 无 |
| 一致性服务 | 参考图选择、首帧抽取、相似度评分 | `/internal/consistency` | MinIO、向量库 |
| 质检模块 | 检测器调度、结果聚合 | `/internal/qc` | FFmpeg、模型 |
| 音频合成 | TTS、混音、响度、字幕 | `/internal/audio` | TTS、FFmpeg |
| 渲染 | 拼装、转码、多规格导出 | `/internal/render` | FFmpeg |
| 存储 | 签名 URL、生命周期、去重 | S3 API 封装 | MinIO |

### 3.2 身份与权限模块

三件事：认证、授权、隔离。

- **认证**：会话 Token（HttpOnly Cookie）或 JWT，二者选一，不要混用。
- **授权**：RBAC，角色 → 权限点，权限点粒度到"能否触发生成""能否交付"。
- **隔离**：所有查询强制带 `project_id` 过滤，在数据访问层实现，不依赖业务代码自觉。

| 角色 | 权限范围 |
|------|---------|
| 制片人 | 项目全量、预算、交付 |
| 编剧 | 剧本与分镜编辑，不可触发生成 |
| 美术 | 资产库、静帧审核 |
| 审片 | 视频审核、重生成 |
| 访客 | 只读预览 |

> 越权最常见的来源不是接口没鉴权，而是接口鉴权了但**没校验项目归属**。统一在 Repository 层加 `project_id` 约束，比在每个 Handler 里写判断可靠。

### 3.3 项目与内容模块

| 子域 | 关键动作 | 约束 |
|------|---------|------|
| 项目 | 创建、设画风、设预算、归档 | 预算为 0 表示不限 |
| 剧本 | 分场、对白、锁定 | 锁定后不可改，需先解锁 |
| 分镜 | 拆镜、重排、改时长、锁镜 | 单镜 ≤ 4s，连续 3 镜禁止同景别 |
| 资产 | 角色卡、风格卡、参考图上传 | 资产变更需重新绑定镜头 |
| 审片 | 通过 / 驳回 / 重生成 | 驳回必须填原因，用于数据回流 |

### 3.4 编排引擎

编排引擎是系统的中枢，负责三件事：**状态推进、门禁校验、失败补偿**。

```python
async def advance(project_id: int) -> None:
    project = await repo.get(project_id)
    while project.state not in TERMINAL_STATES:
        gate = GATES.get(project.state)
        if gate and not await gate.check(project):
            await repo.mark_blocked(project, gate.reason())
            return

        handler = HANDLERS[project.state]
        outcome = await handler.run(project)

        if outcome == "waiting":
            return                      # 依赖异步任务，等回调再推进
        project = await repo.transition(project, NEXT[project.state])
```

三条实现要求：

1. **状态迁移必须落库并带版本号**，用乐观锁防并发推进同一项目。
2. **handler 必须幂等**，重复调用不会产生重复任务（幂等键见 3.5）。
3. **门禁集中配置**，不要散落在业务代码的 `if` 里，否则新同事永远不知道有哪些卡点。

### 3.5 模型网关

网关解决五件事：路由、配额、熔断、幂等、成本。统一抽象如下：

```python
from dataclasses import dataclass
from typing import Protocol, Literal, Any

@dataclass(frozen=True)
class GenRequest:
    step: Literal["text", "still", "video", "tts", "lipsync"]
    model_id: str
    prompt: str
    negative: str
    params: dict[str, Any]
    idempotency_key: str
    project_id: int

@dataclass(frozen=True)
class JobState:
    state: Literal["queued", "running", "succeeded",
                   "failed_retryable", "needs_attention"]
    progress: float
    artifacts: list[str]
    error_code: str | None = None

class Provider(Protocol):
    name: str
    capabilities: set[str]

    async def submit(self, req: GenRequest) -> str: ...
    async def poll(self, task_id: str) -> JobState: ...
    async def cancel(self, task_id: str) -> None: ...
    def estimate(self, req: GenRequest) -> tuple[int, int]:
        """返回 (预估秒数, 预估成本分)"""
        ...
```

路由策略用声明式配置，不要写死在代码里：

| 条件 | 路由目标 | 说明 |
|------|---------|------|
| 默认 | 本地 GPU 池 | 成本最低 |
| 高画质档 / 大分辨率 | 大显存节点 | 避免 OOM |
| 本地池排队超阈值 | 商用 API（备链） | 保交付时效 |
| 节点健康检查失败 | 自动摘除并降级 | 熔断 |
| 项目预算耗尽 | 拒绝并告警 | 预算熔断 |

错误归一化是网关最容易被忽略的价值：把各家不同的错误码统一成 5 类（参数错误 / 资源不足 / 超时 / 内容拦截 / 未知），上层编排才能写出稳定的重试策略。

### 3.6 提示词编译器

提示词不要手写拼接，用编译器分层合成，便于统一控制权重与冲突：

```text
最终提示词 = 风格层 + 角色层 + 镜头层 + 动作层 + 光照层
负面提示词 = 全局负面库 ∪ 镜头级负面（去重后取并集）
```

| 层 | 来源 | 示例 | 权重 |
|----|------|------|------|
| 风格层 | 风格卡 | 国漫、赛璐璐上色、厚涂质感 | 1.0 |
| 角色层 | 角色卡 | 玄色圆领袍、玉冠、冷白肤色 | 1.2 |
| 镜头层 | 镜头 | 特写、浅景深、居中构图 | 1.0 |
| 动作层 | 镜头动作 | 缓慢睁眼、发丝飘动 | 1.1 |
| 光照层 | 场次 | 冷月光侧逆光、低照度 | 0.9 |

冲突消解规则写死：同一属性出现两次时**高权重覆盖低权重**，而不是堆叠——堆叠会出现"玄色官服 + 白色长袍"这种自相矛盾的提示词，模型只能随机二选一。

### 3.7 一致性服务

一致性服务是"资产 → 生成参数"的转换器，对外提供三个能力：

| 能力 | 输入 | 输出 |
|------|------|------|
| 组装生成上下文 | 镜头 + 角色卡 + 风格卡 | 提示词、参考图列表、适配器参数 |
| 首帧选择 | 当前镜头 + 前一镜产物 | 首帧图 URI（末帧 / 重出图 / 上传） |
| 一致性打分 | 产物 + 参考图 | 人脸 / 语义 / 风格三项分数 |

一致性度量建议用三条可落地指标，阈值必须用自己项目的数据标定：

| 指标 | 方法 | 经验阈值 |
|------|------|---------|
| 人脸相似度 | 人脸 embedding 余弦相似度 | ≥ 0.72 |
| 画面语义相似度 | DINOv2 / CLIP 图像 embedding | ≥ 0.60 |
| 风格相似度 | CLIP 图像 embedding 对比风格参考图 | ≥ 0.65 |

做法：先人工标 100 张"通过 / 不通过"，再调阈值让自动判定与人工判定一致率最高。**没有标定的阈值等于没有阈值。**

### 3.8 质检模块

质检用规则引擎 + 可插拔检测器，不要写成一个巨大的 `if-else`：

```python
class Detector(Protocol):
    name: str
    severity: Literal["block", "warn"]

    async def run(self, artifact: Artifact, ctx: QcContext) -> QcFinding: ...
```

| 检测器 | 方法 | 级别 |
|--------|------|------|
| 黑帧 / 静帧 | 帧差 + 亮度统计 | block |
| 人脸崩坏 | 人脸检测失败 / 多脸 | block |
| 水印文字 | OCR + 文本区域检测 | block |
| 镜头跳变 | 帧间直方图突变 | warn |
| 音画同步 | 对白起止与动作对齐 | warn |
| 首尾衔接 | 相邻镜首末帧相似度 | warn |
| 时长偏差 | 实际 vs 分镜时长 | warn |

`block` 直接拦下进入重生成队列，`warn` 只提示人工复核。检测器并发执行，单个超时不阻塞整体——质检本身也要有超时保护。

### 3.9 音频与合成模块

| 子能力 | 实现要点 |
|--------|---------|
| 分句 | 按标点 + 语义切分，单句 ≤ 20 字便于对齐 |
| TTS | 角色绑定音色 ID，支持情绪与语速参数 |
| 时长表 | 实测每句音频时长，写回 `shot.duration_ms` |
| 口型 | 特写对白镜才做，其余用侧脸 / 背影 / 拉远规避 |
| 混音 | 对白优先，BGM 侧链闪避，响度 -16 LUFS |
| 字幕 | 由配音时间轴生成 ASS，随片烧制 |

### 3.10 模块契约：错误码与事件

统一错误码，避免上层猜语义：

| 错误码 | 含义 | 是否重试 |
|--------|------|---------|
| `E_PARAM` | 参数非法 | 否 |
| `E_QUOTA` | 配额 / 预算不足 | 否 |
| `E_OOM` | 显存不足 | 降档重试一次 |
| `E_NODE_DOWN` | 节点不可用 | 是 |
| `E_TIMEOUT` | 执行超时 | 是 |
| `E_CONTENT` | 内容安全拦截 | 否 |
| `E_UNKNOWN` | 提交结果未知 | 转 `needs_attention` |

领域事件表：

| 事件 | 触发时机 | 订阅方 |
|------|---------|-------|
| `shot.still.approved` | 静帧审核通过 | 编排引擎 |
| `shot.video.approved` | 视频审核通过 | 编排引擎 |
| `job.failed` | 任务终态失败 | 通知、看板 |
| `budget.threshold` | 预算达 80% / 100% | 告警、熔断 |
| `episode.rendered` | 成片产出 | 交付模块 |

## 四、数据流设计

### 4.1 全链路主流程

```
用户      API        编排        网关        Worker     ComfyUI     存储
 │ 建项目  │          │           │           │          │          │
 │────────►│ 落库     │           │           │          │          │
 │         │─────────►│ 初始化状态 │           │          │          │
 │ 触发S6  │          │           │           │          │          │
 │────────►│ 建 job   │           │           │          │          │
 │         │─────────►│ 门禁校验   │           │          │          │
 │         │          │──────────►│ 路由/配额  │          │          │
 │         │          │           │──────────►│ 原子扣单  │          │
 │         │          │           │           │─────────►│ 执行推理  │
 │         │◄──SSE────┼───────────┼───────────│◄──进度────│          │
 │         │          │◄──────────┼───────────│ 产物上传 ─┼─────────►│
 │         │          │◄──────────┼───────────│ 写血缘    │          │
 │ 审片    │          │ 推进状态   │           │          │          │
 │────────►│─────────►│           │           │          │          │
```

### 4.2 单镜头生成的九步数据流

以静帧生成为例，每一步都要定义**失败分支**：

| 步 | 动作 | 数据变化 | 失败分支 |
|----|------|---------|---------|
| 1 | 前端提交生成请求 | 生成 `idempotency_key` | 参数校验失败 → `E_PARAM` |
| 2 | 应用层建 job | `jobs` 插入 `queued` | 幂等键冲突 → 直接返回已有 job |
| 3 | 编排层校验门禁 | 读 `shots.state` | 门禁未过 → 拒绝并提示缺失项 |
| 4 | 网关路由与配额 | 读项目预算、节点健康 | 超预算 → `E_QUOTA` |
| 5 | Worker 原子扣单 | 置 `running` + 租约 | 抢不到 → 空闲等待 |
| 6 | 组装生成上下文 | 读角色卡、风格卡、上一镜产物 | 资产缺失 → 阻断 |
| 7 | 提交 ComfyUI | 写 `prompt_id` 到 job | 显存不足 → `E_OOM` 降档重试 |
| 8 | 产物上传对象存储 | 写 `artifacts` + `lineage` | 上传失败 → 重传，不重复生成 |
| 9 | 状态回写 + 事件 | job → `succeeded`，镜头 → 待审 | 超时 → 租约回收重排 |

> 第 8 步的"上传失败不重复生成"很关键：推理结果先落本地临时目录，上传是独立可重试步骤。否则一次网络抖动就要重跑几分钟的 GPU 任务。

### 4.3 事件流与进度推送

前端不轮询数据库，改用 SSE。事件结构固定：

```json
{
  "event": "job.progress",
  "job_id": 88213,
  "project_id": 42,
  "shot_id": 3012,
  "step": "video",
  "state": "running",
  "progress": 0.62,
  "eta_seconds": 84,
  "ts": "2026-11-24T10:21:35+08:00"
}
```

| 事件 | 前端动作 |
|------|---------|
| `job.queued` | 卡片置灰，显示排队位次 |
| `job.progress` | 更新进度条与预估剩余 |
| `job.succeeded` | 拉取产物签名 URL，切到待审 |
| `job.failed` | 显示错误码与可执行动作 |
| `job.needs_attention` | 高亮，要求人工确认 |

SSE 连接数需要单独监控：一集 80 镜同时跑，前端可能开多条流，要按 `project_id` 做频道合并。

### 4.4 数据分层与生命周期

| 数据 | 存放 | 保留策略 |
|------|------|---------|
| 结构化业务数据 | PostgreSQL | 长期，按项目归档 |
| 生成参数快照 | PostgreSQL JSONB | 永久 |
| 中间产物（未通过的图/视频） | 对象存储 | 30 天，可配置 |
| 通过的分镜产物 | 对象存储 | 项目归档后转低频 |
| 成片 | 对象存储 + CDN | 长期 |
| 提示词模板 / 工作流 | 数据库 + Git | 永久，带版本 |
| 日志 | 日志系统 | 30–90 天 |

## 五、领域模型与数据设计

### 5.1 核心实体

```
Project ─┬─ Episode ─┬─ Scene ─── Shot ──┬─ StillArtifact
         │           │                   └─ VideoArtifact
         │           └─ AudioTrack
         ├─ Character ── ReferenceImage
         ├─ StyleCard
         └─ Job ── Artifact ── Lineage
```

| 实体 | 职责 | 关键字段 |
|------|------|---------|
| Project | 一部作品 | 画风、比例、预算、状态 |
| Episode | 一集 | 集号、时长目标、成片 URI |
| Scene | 一场戏 | 地点、时间、情绪基调 |
| Shot | 一个镜头 | 景别、运镜、时长、提示词、状态 |
| Character | 角色卡 | 外观锚点、参考图集、适配器绑定 |
| StyleCard | 风格卡 | 风格标签、参考图、负面词库 |
| Job | 一次生成任务 | 步骤、参数快照、状态、重试次数 |
| Artifact | 产物 | 类型、URI、哈希、尺寸、时长 |
| Lineage | 血缘 | 输入产物、模型哈希、工作流版本、种子 |

### 5.2 关键表设计

```sql
CREATE TABLE projects (
    id            BIGSERIAL PRIMARY KEY,
    title         TEXT NOT NULL,
    style_card_id BIGINT REFERENCES style_cards(id),
    aspect_ratio  TEXT NOT NULL DEFAULT '9:16',
    budget_cents  BIGINT NOT NULL DEFAULT 0,
    state         TEXT NOT NULL DEFAULT 'draft',
    version       INT NOT NULL DEFAULT 0,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE shots (
    id             BIGSERIAL PRIMARY KEY,
    episode_id     BIGINT NOT NULL REFERENCES episodes(id),
    scene_id       BIGINT REFERENCES scenes(id),
    seq            INT NOT NULL,
    shot_size      TEXT,
    camera_move    TEXT,
    duration_ms    INT NOT NULL,
    dialogue       TEXT,
    prompt_visual  JSONB NOT NULL,
    prompt_motion  JSONB,
    state          TEXT NOT NULL DEFAULT 'pending',
    locked         BOOLEAN NOT NULL DEFAULT false,
    UNIQUE (episode_id, seq)
);

CREATE TABLE artifacts (
    id          BIGSERIAL PRIMARY KEY,
    kind        TEXT NOT NULL,
    uri         TEXT NOT NULL,
    sha256      TEXT NOT NULL,
    width       INT,
    height      INT,
    duration_ms INT,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE jobs (
    id              BIGSERIAL PRIMARY KEY,
    project_id      BIGINT NOT NULL,
    shot_id         BIGINT REFERENCES shots(id),
    step            TEXT NOT NULL,
    priority        INT NOT NULL DEFAULT 100,
    state           TEXT NOT NULL DEFAULT 'queued',
    attempt         INT NOT NULL DEFAULT 0,
    max_attempt     INT NOT NULL DEFAULT 3,
    run_after       TIMESTAMPTZ NOT NULL DEFAULT now(),
    lease_until     TIMESTAMPTZ,
    idempotency_key TEXT UNIQUE NOT NULL,
    request         JSONB NOT NULL,
    result          JSONB,
    error_code      TEXT,
    cost_cents      INT NOT NULL DEFAULT 0,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_jobs_claim ON jobs (state, priority DESC, run_after);
```

> `request` 是不可变快照。任务入队后用户改了提示词，不能让队列里的任务偷偷用新参数跑——否则一条任务记录会对应两个不同产物，血缘就断了。**改参数等于新建任务。**

### 5.3 三套状态机

```text
项目：draft → scripting → storyboarding → generating → reviewing → rendering → delivered
                                     ↘ blocked（任一阶段门禁未过）

镜头：pending → prompt_ready → still_pending → still_approved
                              → video_pending → video_approved
                              → audio_ready → approved

任务：queued → running → succeeded
                     ├→ failed_retryable
                     ├→ needs_attention
                     └→ canceled
```

`needs_attention` 单独存在的原因是：**提交到 GPU 节点后连接断开、无法确认是否真的开始生成时，不能直接判失败重试**，否则会重复扣算力、重复占显存，甚至产出两份不一致结果。此时挂起等人确认，比自动重试十次便宜。

### 5.4 阶段门禁

| 门禁 | 规则 | 失败动作 |
|------|------|---------|
| 进 S6 | 剧本锁定 + 角色卡定稿 | 阻断，提示缺失项 |
| 进 S7 | 该镜静帧已通过 | 只跑已通过的镜头 |
| 进 S10 | 全部镜头视频通过 + 音轨锁定 | 阻断，列出未通过镜头 |
| 进 S11 | 质检分 ≥ 阈值 | 进入人工终审 |

### 5.5 血缘与复现

复现取决于三样东西是否完整：**模型哈希**（不是模型名）、**工作流版本 + 哈希**、**参数快照 + 种子**。缺任何一样，只能说"大概能重现"。

> seed 不能保证逐像素复现。不同显卡、驱动、CUDA 版本、attention 实现都会带来数值差异。正确的承诺是"同模型同工作流同参数，视觉等价"，而不是"比特一致"。

## 六、剧本与分镜：把创作变成结构化数据

### 6.1 为什么必须结构化

如果剧本、分镜、提示词都是自由文本，系统只能当"记事本 + 生成按钮"，无法做到批量重生成、按镜替换、跨集复用角色、统计通过率、自动拼装。

结构化之后，一个镜头就是一行可计算的数据：

```yaml
episode: 1
title: 司天署
style_card: ancient_cn_comic_v3
scenes:
  - id: sc01
    location: 司天署·观星台
    time: 夜
    mood: 压抑、悬疑
    shots:
      - seq: 1
        size: 特写
        camera: 缓慢推近
        duration_ms: 2400
        dialogue: "（无对白）"
        visual:
          subject: "青年男主，玄色官服，抬头睁眼"
          composition: "面部居中偏左，背景为星图"
          lighting: "冷月光侧逆光"
        motion: "眼睑缓慢睁开，发丝轻微飘动，镜头稳定推近"
        negative: ["text", "watermark", "extra fingers"]
```

每个字段都有明确用途：`duration_ms` 决定视频帧数，`dialogue` 决定配音与口型，`visual.subject` 进提示词，`negative` 参与负面词合并。

### 6.2 从小说到分镜的三段式

| 段 | 输入 | 输出 | 约束 |
|----|------|------|------|
| 改编 | 原文 / 大纲 | 分集大纲 | 只做取舍，不改人设 |
| 分场 | 单集大纲 | 场次表 | 场次 ≤ 8，单场 ≤ 25 秒 |
| 拆镜 | 场次表 + 时长表 | 镜头表 JSON | 单镜 ≤ 4s，禁止连续 3 镜同景别 |

工程上注意三点：

1. **用 JSON Schema 约束输出**，解析失败直接重试，不要用正则去救文本。
2. **把时长表喂给 LLM**，让它按"台词字数 ÷ 语速"填，而不是自己算。
3. **保留人工编辑层**，AI 只出草稿，最终以库里数据为准。

### 6.3 分镜的可编辑性与 diff

分镜表支持镜头级增删改、拖拽重排、锁镜。锁定后的镜头在批量重生成时跳过，避免已经满意的镜头被覆盖。

结构性变更要能 diff：新增 / 删除 / 时长变化 / 提示词变化分别高亮，便于审阅"这一版改了什么"。

## 七、一致性：漫剧的生死线

### 7.1 一致性的四层来源

| 层 | 表现 | 主要成因 |
|----|------|---------|
| 角色 | 换脸、发型变化、服装变色 | 无参考图、提示词漂移、不同 seed |
| 风格 | 某镜突然写实 / 3D | 风格标签未锁定、模型混用 |
| 构图 | 越轴、景别跳变、视线不接 | 分镜无连贯性约束 |
| 时序 | 上一镜向左走，下一镜向右 | 首帧未继承、运镜描述冲突 |

前两层靠资产 + 技术手段解决，后两层靠分镜规则 + 首帧链解决。只做前两层，角色很稳但成片"看着别扭"，问题通常出在后两层。

### 7.2 角色卡与风格卡

```yaml
character: male_lead
name: 沈砚
anchors:
  face: "窄脸、高鼻梁、细长眼、冷白皮"
  hair: "黑发束冠，两缕垂鬓"
  costume: "玄色圆领窄袖袍，暗金云纹"
  signature: "左手拇指戴墨玉扳指"
reference_images:
  - s3://assets/male_lead/ref_front.png
  - s3://assets/male_lead/ref_side.png
adapter:
  type: ip_adapter
  weight: 0.65
  target: face_and_costume
lora:
  name: shen_yan_v2
  weight: 0.8
```

`signature` 是经验字段：给角色加一个**小而独特的视觉锚点**（扳指、疤痕、耳饰），比堆十条外貌描述更能稳定识别，也方便观众认人。

### 7.3 技术手段矩阵

| 手段 | 作用 | 成本 | 适用 |
|------|------|------|------|
| 提示词锁定 + 固定 seed | 基础稳定 | 极低 | 全部 |
| 参考图 + IP-Adapter | 角色 / 风格迁移 | 低 | 角色主视角 |
| LoRA 微调 | 高保真角色还原 | 中（需训练） | 主角、高频角色 |
| ControlNet | 控制构图与动作 | 中 | 关键动作镜 |
| 首帧继承 | 时序连贯 | 低 | 连续动作 |
| 参考图打分筛选 | 出图后择优 | 低 | 静帧批量 |

组合策略：**主角用 LoRA + 参考图，配角用 IP-Adapter，风格全局用风格卡，连续动作镜走首帧继承。**

### 7.4 首帧继承链

```
镜1 生成 ──► 静帧1 ──► 视频1
                        │
                        └─ 抽取末帧 ──► 镜2 首帧 ──► 视频2 ──► ...
```

两个坑：**误差累积**（连抽 5 次末帧画面会糊，建议每 3–5 镜回到角色卡重置一次）；**末帧质量**（末帧有运动模糊或遮挡会传染下一镜，需过质量分，不达标退回用静帧重新生成）。

## 八、生成执行：队列与工作流

### 8.1 任务队列

起步用数据库队列最省事，`SKIP LOCKED` 保证多 Worker 不抢同一任务：

```sql
UPDATE jobs
SET state = 'running',
    lease_until = now() + interval '10 minutes',
    attempt = attempt + 1
WHERE id = (
    SELECT id FROM jobs
    WHERE state = 'queued'
      AND run_after <= now()
    ORDER BY priority DESC, created_at
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
RETURNING *;
```

三条规则：

1. **租约而非心跳**：Worker 挂了租约到期任务自动回队，不需要人工捞。
2. **重试分类且封顶**：显存不足降档重试一次；节点掉线可重试；参数错误不重试。
3. **同镜串行**：同一 `shot_id` 的静帧与视频不能并发，否则互相踩显存、结果乱序。

### 8.2 ComfyUI 工作流模板化

不要每次现场拼工作流 JSON，用模板 + 参数注入：

```json
{
  "workflow": "i2v_base",
  "version": "3.7.2",
  "bindings": {
    "12.inputs.text": "$positive",
    "13.inputs.text": "$negative",
    "21.inputs.image": "$first_frame",
    "31.inputs.seed": "$seed",
    "31.inputs.steps": "$steps"
  }
}
```

三条硬规则：工作流带版本号并算哈希写入血缘；模型文件名映射到权重哈希；提交前做显存预检，不足直接返回资源不足，而不是等 OOM 把节点拖崩。

### 8.3 失败处理语义

| 失败类型 | 判定依据 | 处理 |
|---------|---------|------|
| 参数错误 | 校验失败 | 不重试，直接失败 |
| 显存不足 | OOM 关键字 | 降分辨率重试一次，仍失败则排队等待 |
| 节点超时 | 超过租约 | 可重试，最多 3 次 |
| 提交未知 | 连接中断且查不到状态 | `needs_attention`，人工确认 |
| 结果质量差 | 质检不通过 | 不算失败，进入重生成队列 |

## 九、音频与后期

### 9.1 先音后画

正确顺序是：**对白 TTS → 时长表 → 分镜 → 生成 → 对齐 → 混音**。

```text
剧本对白
  └─► 分句（按标点 + 语义）
        └─► TTS（角色音色 + 情绪）
              └─► 实测每句时长 ──► 写入 shot.duration_ms
                    └─► 分镜按实际时长切
```

TTS 要解决三件事：音色一致性（跨集同一音色 ID）、情绪控制、语速可调。

### 9.2 口型同步

| 方案 | 做法 | 效果 | 成本 |
|------|------|------|------|
| 不做口型 | 身体微动 + 镜头运动 | 漫剧可接受 | 0 |
| 简单开合 | 音素能量驱动嘴部 | 中等 | 低 |
| 模型驱动 | 音频驱动人脸 | 高 | 中高 |

多数项目停在第二档即可。必须做口型的只有特写对白镜，其余用侧脸 / 背影 / 拉远规避，是性价比最高的工程手段。

### 9.3 混音与合成标准

| 项 | 目标值 | 说明 |
|----|--------|------|
| 整体响度 | -16 LUFS | 短视频平台通用 |
| 真峰值 | ≤ -1.5 dBTP | 防削波 |
| 对白 / BGM | 对白优先，BGM 自动闪避 | 侧链压缩 |
| 音效对齐 | ±80ms | 超出即感知不同步 |

```bash
ffmpeg -y -f concat -safe 0 -i clips.txt -i bgm.wav \
  -filter_complex "\
[0:v]scale=1080:1920:flags=lanczos,fps=24,ass=ep01.ass[v];\
[1:a]loudnorm=I=-16:TP=-1.5:LRA=11[bgm];\
[0:a][bgm]amix=inputs=2:duration=first:dropout_transition=2,\
alimiter=limit=0.95[a]" \
  -map "[v]" -map "[a]" \
  -c:v libx264 -preset slow -crf 18 -pix_fmt yuv420p \
  -c:a aac -b:a 192k -movflags +faststart \
  ep01_final.mp4
```

生成侧的低帧率不要直接交付，用插帧补到 24fps 更"顺"。注意插帧只解决流畅度，清晰度要靠超分。

## 十、质量门禁与人工审片

### 10.1 自动质检

自动质检不是为了替代人，而是把人从明显废片里解放出来。检测项见 3.8 节，这里强调三条工程原则：

1. **检测器并发 + 单点超时**，不让一个慢检测器拖住整集。
2. **结论要可解释**，输出"哪一帧、什么原因、置信度"，而不是只给一个分数。
3. **阈值可配置**，不同题材、不同画风的容忍度不一样。

### 10.2 人审工作台

审片界面的信息密度决定人效。必须同屏看到：当前镜的静帧、视频、提示词、参数、seed；相邻镜的末帧 / 首帧；一键"重生成 / 换 seed / 微调后重生成 / 通过"；键盘快捷键（通过 `J`、重生成 `K`、下一个 `L`）。

> 审片是最耗时的人工环节。单镜审片从 20 秒压到 8 秒，一集能省 10 分钟以上，这是最值得投入的"非 AI"优化。

### 10.3 数据回流

每次重生成都记录原因：人脸崩、构图差、动作僵硬、时长不符、风格漂移。这些统计直接指导提示词模板与参数调整，是系统长期变好的唯一闭环。

## 十一、算力、成本与性能

### 11.1 单镜耗时参考

以下为工程估算区间，实际以自测为准：

| 环节 | 硬件 | 单镜耗时 | 备注 |
|------|------|---------|------|
| 静帧 1024×1536 / 40 步 | RTX 4090 24G | 4–7 s | 批量 4 张取优 |
| 静帧 FP8 | RTX 4060 8G | 15–25 s | 需 block swap |
| I2V 480×832 / 81 帧 | RTX 4090 | 2–4 min | 14B FP8 |
| I2V 720×1280 / 121 帧 | A100 80G | 4–7 min | 序列分块 |
| TTS 单句 | CPU / GPU | 0.3–1 s | 流式合成 |
| 插帧 + 超分 | GPU | 0.5–1.5× 原时长 | 可离线批处理 |
| 转码 3 分钟成片 | CPU | 30–90 s | preset slow |

### 11.2 成本模型

```text
单镜成本 = (静帧耗时 × 静帧单价 + 视频耗时 × 视频单价) × (1 + 重生成率)
集成本   = Σ 单镜成本 + TTS + 混音 + 插帧超分 + 转码 + 存储
项目成本 = Σ 集成本 + 人工审片工时（单独统计，不进算力账）
```

按 80 镜 / 集、重生成率 1.8 估算：

| 项 | 估算值 |
|----|--------|
| 视频生成 | 80 × 3min × 1.8 ≈ 7.2 GPU 小时 |
| 静帧生成 | 80 × 6s × 1.8 ≈ 0.24 GPU 小时 |
| GPU 租赁（约 ¥3/h） | ≈ ¥22 |
| 音频 + 转码 + 存储 | ≈ ¥8–15 |
| **算力合计** | **≈ ¥30–40 / 集** |
| 人工审片 | 4–8 人时（真正的大头） |

> 结论：**算力很便宜，人很贵。** 优化优先级应是：先降重生成率（模板 + 一致性），再降审片时间（工作台 + 快捷键），最后才考虑省 GPU。

### 11.3 调度策略

| 策略 | 做法 | 收益 |
|------|------|------|
| 优先级 | 审片中的镜头 > 新生成 > 批处理补镜 | 缩短人机等待 |
| 批量静帧 | 同项目同角色批量串行出图 | 减少模型反复加载 |
| 错峰 | 插帧 / 超分 / 转码放夜间 | 不与交互任务抢卡 |
| 缓存复用 | 提示词哈希 + 参数哈希命中则复用 | 改一镜不必重跑全片 |

### 11.4 显存墙

8GB 卡跑 14B 视频模型必须取舍：降分辨率、降帧数、FP8 量化、block swap、串行任务。**不要绕过显存预检硬跑**——一次 OOM 可能导致整个节点重启，损失远大于排队等待。

## 十三、API 设计

### 13.1 接口风格

- 写操作同步返回（创建项目、保存分镜），生成类操作异步返回 `job_id`。
- 进度用 SSE 推送，不轮询数据库——一集 80 镜轮询会把库打满。
- 所有生成接口必须携带幂等键，防止重复点击产生重复任务。

### 13.2 关键接口

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/projects` | 创建项目 |
| GET | `/api/projects/{id}/pipeline` | 查看 S0–S11 阶段状态 |
| PUT | `/api/shots/{id}` | 编辑镜头（提示词/时长/运镜） |
| POST | `/api/shots/{id}/generate` | 生成静帧或视频，返回 job_id |
| POST | `/api/jobs/{id}/retry` | 重试（仅 failed_retryable） |
| POST | `/api/jobs/{id}/resolve` | 处理 needs_attention |
| GET | `/api/jobs/{id}/events` | SSE 进度流 |
| POST | `/api/episodes/{id}/render` | 拼装整集 |
| GET | `/api/episodes/{id}/qc` | 质检报告 |

生成请求示例：

```json
{
  "step": "still",
  "shot_id": 3012,
  "model_id": "sdxl_realvis_v5",
  "params": { "width": 1024, "height": 1536, "steps": 40, "cfg": 5.5 },
  "idempotency_key": "still-3012-r3"
}
```

### 13.3 工作台信息架构

```text
项目列表
└─ 项目详情
   ├─ 概览（阶段进度 / 成本 / 未通过镜头）
   ├─ 剧本与分镜（可编辑表格 + 镜头卡片）
   ├─ 资产库（角色卡 / 风格卡 / 参考图）
   ├─ 生成队列（运行中 / 失败 / 待处理）
   ├─ 审片（静帧审 / 视频审 / 键盘流）
   └─ 交付（多规格导出 / 质检报告）
```

## 十四、部署方案

### 14.1 单机版：Compose 起全栈

适用个人验证与小团队试用，一台带 GPU 的 Linux 机器即可。

```yaml
services:
  api:
    build: .
    ports: ["8080:8080"]
    environment:
      DATABASE_URL: postgresql://app:app@db:5432/app
      REDIS_URL: redis://redis:6379/0
      S3_ENDPOINT: http://minio:9000
    depends_on: [db, redis, minio]

  worker:
    build: .
    command: python -m app.workers.main
    environment:
      DATABASE_URL: postgresql://app:app@db:5432/app
      COMFY_URL: http://comfy:8188
    depends_on: [db, redis, comfy]
    deploy:
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]

  comfy:
    image: comfyui/comfyui:latest
    ports: ["8188:8188"]
    volumes:
      - "${MODEL_DIR}:/models"
      - "./workflows:/workflows"

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app
      POSTGRES_DB: app
    volumes: ["pgdata:/var/lib/postgresql/data"]

  redis:
    image: redis:7
    volumes: ["redisdata:/data"]

  minio:
    image: minio/minio
    command: server /data --console-address ":9001"
    environment:
      MINIO_ROOT_USER: app
      MINIO_ROOT_PASSWORD: change-me
    volumes: ["miniodata:/data"]

volumes:
  pgdata: {}
  redisdata: {}
  miniodata: {}
```

要点：模型目录用宿主机挂载（不要在容器里重复下载几十 GB 权重）；ComfyUI 必须做 `/system_stats` 健康检查；数据库与对象存储的数据卷要落在独立磁盘。

### 14.2 工作室版：API 机 + 多 GPU 节点

```
        ┌──────────────┐
        │  API / Web   │  无公网 GPU
        └──────┬───────┘
   ┌───────────┼────────────┐
┌──▼───┐   ┌───▼────┐   ┌───▼────┐
│ PG   │   │ Redis  │   │ MinIO  │
└──────┘   └────────┘   └───┬────┘
        ┌───────────────────┘
   ┌────▼─────┐  ┌─────────┐  ┌─────────┐
   │ GPU-01   │  │ GPU-02  │  │ GPU-03  │
   │ Worker   │  │ Worker  │  │ Worker  │
   │ ComfyUI  │  │ ComfyUI │  │ ComfyUI │
   └──────────┘  └─────────┘  └─────────┘
```

GPU 节点安装 `nvidia-container-toolkit` 后单独启动 Worker + ComfyUI：

```bash
docker run -d --gpus all --name comic-gpu-01 \
  -v /data/models:/models:ro \
  -v /data/workflows:/workflows:ro \
  -e API_BASE=http://api.internal:8080 \
  -e NODE_NAME=gpu-01 \
  --restart unless-stopped \
  registry.local/comic-gpu:1.4.0
```

| 要点 | 说明 |
|------|------|
| 节点注册 | Worker 启动后向 API 注册，上报显卡型号、显存、模型清单 |
| 健康检查 | 每 15 秒探测 ComfyUI，连续 3 次失败自动摘除 |
| 模型分发 | 模型目录只读挂载，统一由运维预置，禁止节点自行下载 |
| 网络 | GPU 节点只开内网，不暴露公网端口 |

### 14.3 集群版：Kubernetes

规模上来后，把 API、Worker、ComfyUI 分别做成工作负载，GPU 用节点池隔离。

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: worker-gpu
spec:
  replicas: 3
  selector:
    matchLabels:
      app: worker-gpu
  template:
    metadata:
      labels:
        app: worker-gpu
    spec:
      nodeSelector:
        pool: gpu
      containers:
        - name: worker
          image: registry.local/comic-worker:1.4.0
          resources:
            limits:
              nvidia.com/gpu: 1
              memory: 32Gi
          volumeMounts:
            - name: models
              mountPath: /models
              readOnly: true
      volumes:
        - name: models
          persistentVolumeClaim:
            claimName: model-pvc
```

| 组件 | 工作负载 | 伸缩依据 |
|------|---------|---------|
| API | Deployment | CPU / QPS |
| Worker-CPU | Deployment | 队列积压 |
| Worker-GPU | Deployment（1 卡 1 副本） | 队列积压 + GPU 空闲 |
| ComfyUI | Deployment 或 DaemonSet | 跟随 GPU 节点 |
| PG / Redis / MinIO | StatefulSet / 托管服务 | 容量 |

注意：**GPU 副本的伸缩要慢**。新 Pod 拉起后要加载十几 GB 权重，冷启动可能需要几分钟，HPA 的窗口要按分钟级配置，不要用秒级抖动触发扩容。

### 14.4 存储与备份

| 项 | 方案 |
|----|------|
| 数据库 | 每日全量 `pg_dump` + WAL 归档，保留 7 天全量 + 30 天增量 |
| 对象存储 | 开启版本化，成片与通过的分镜产物永不删除 |
| 中间产物 | 生命周期 30 天自动清理 |
| 恢复演练 | 每季度做一次"空库 + 备份"恢复验证，记录 RTO |
| 配置与工作流 | Git 管理，随发布打标签 |

### 14.5 网络与安全

| 项 | 要求 |
|----|------|
| 边界 | 只暴露 API 与静态资源，GPU 节点与数据库仅内网 |
| 传输 | 全站 HTTPS；内网可选 mTLS |
| 对象访问 | 一律签名 URL，有效期 10–30 分钟，禁止公开桶 |
| 密钥 | 环境变量注入或密钥管理服务，禁止写进镜像 |
| 内容安全 | 生成前后双向审核，命中阻断并留痕 |
| 深度合成标识 | 成片添加显式标识 + 元数据隐式标识 |
| 版权 | 参考图、BGM、音效登记授权来源；模型逐一核验商用许可 |
| 审计 | 登录、生成、下载、删除全部记审计日志 |

### 14.6 容量规划

```text
并发生成数   = GPU 数 × 单卡并行数（视频通常为 1）
日产能（镜） = GPU 数 × 86400 / 单镜平均耗时 × 利用率
日产能（集） = 日产能（镜） / 每集镜头数
```

以 4 张卡、单镜平均 180 秒、利用率 75%、每集 80 镜为例：

```text
日产能 ≈ 4 × 86400 / 180 × 0.75 ≈ 1440 镜 ≈ 18 集/天（理论值）
按重生成率 1.8 折算 ≈ 10 集/天（实际可用值）
```

规划时用"实际可用值"，不要用理论峰值，否则永远在救火。

### 14.7 发布与回滚

1. **数据库迁移先行且向后兼容**：先加字段、双写、再切读、最后删旧字段，禁止一次性破坏性变更。
2. **工作流版本并存**：新工作流以新版本号上线，历史项目继续用旧版本，避免"昨天的片子今天复现不了"。
3. **灰度按项目**：先让 1–2 个项目切新版本，观察一次通过率与失败率，再全量。
4. **回滚只回代码不回数据**：镜像回滚即可，数据迁移保持兼容。

### 14.8 上线检查清单

| 项 | 验收标准 |
|----|---------|
| 全链路 | 从建项目到导出成片可完整跑通 |
| 失败恢复 | 杀掉 Worker 后任务能自动回队并被接管 |
| 幂等 | 重复点击生成不产生重复任务 |
| 显存保护 | 显存不足返回明确错误，不影响其他任务 |
| 备份恢复 | 空环境可用备份还原并跑通 |
| 权限 | 跨项目访问被拒绝 |
| 成本 | 单集成本可查询、可持续累计 |
| 合规 | 成片带深度合成标识，素材有授权记录 |

## 十五、开发路线图

### 15.1 三阶段交付

| 阶段 | 范围 | 交付物 | 验收标准 |
|------|------|--------|---------|
| MVP | S0–S7 + 单机队列 | 能出一集 30 秒样片 | 全链路可跑通，失败可重试 |
| V1 | 补 S3 音频、S8 质检、S10 拼装 | 能交付 1–3 分钟完整集 | 一次通过率 ≥ 60%，成片有音轨有字幕 |
| V2 | 多项目、权限、成本核算、集群 | 可并行生产 | 单集交付 ≤ 2 天，成本可核算 |

### 15.2 每阶段明确"不做什么"

- MVP 不做多租户、不做集群、不做 LoRA 训练、不做口型同步。
- V1 不做自动剪辑、不做多语言配音、不做商用 API 自动切换。
- V2 不做实时预览、不做端到端全自动。

> 路线图最大的价值不是"要做什么"，而是明确写出"这一期不做什么"。没有这句，范围一定失控。

## 十六、常见坑与对策

**Q1：为什么不一开始就上微服务？**

瓶颈是 GPU 和人工，不是接口并发。微服务会把"改一行本地验证"变成"起 6 个容器才能调试"，在流程未稳定时是纯负债。

**Q2：为什么一定要先音后画？**

配音时长是唯一客观的节奏基准。先画后配等于用主观估计对齐客观时长，返工不可避免。

**Q3：为什么 seed 不能保证复现？**

不同硬件、驱动、CUDA、attention 实现存在数值差异。能承诺的是"同模型同工作流同参数，视觉等价"。

**Q4：8GB 显存还能做吗？**

能，但要取舍：480×832、2–4 秒、FP8、block swap、严格串行、显存预检。适合验证，不适合量产。

**Q5：为什么需要 `needs_attention` 状态？**

"提交结果未知"与"确定失败"是两回事。前者若直接重试，会重复扣算力、重复占显存、产出两份不一致结果。

**Q6：为什么不直接买商用视频 API？**

可以，适合起步验证。但要注意：单镜成本随镜头数线性增长、工作流无法锁版本、内容审核策略不可控。自建 + 商用兜底通常是更稳的组合。

**Q7：审片为什么慢？**

因为信息不全，人要在多个页面之间来回找。把静帧、视频、提示词、相邻镜头、操作按钮放一屏，配合快捷键，单镜耗时能降一半以上。

**Q8：怎么判断系统够用了？**

看三个数：一次通过率 ≥ 60%、单集交付 ≤ 2 天、单分钟成本可接受。都达标再扩量。

## 十七、总结

把 AI 漫剧系统做"专业"，不在于用了多新的模型，而在于把一件创作性的工作拆成了**可计算、可重试、可审计**的工程流程。

整套方案里真正起作用的只有六件事：

1. **架构上依赖单向**，分层清晰，换模型换存储不伤业务。
2. **流程上先音后画**，让配音时长成为分镜的唯一时钟。
3. **数据上一切结构化**，剧本、分镜、资产、提示词都能 diff、回滚、复用。
4. **一致性上分层治理**，角色靠资产、时序靠首帧链、构图靠分镜规则。
5. **工程上编排与执行分离**，网关收口模型，队列保证重试语义，血缘保证复现。
6. **部署上按规模演进**，单机 → 工作室 → 集群，每一步都有明确的演进信号。

先让链路跑通，再让链路可靠，最后让链路划算。顺序错了，前面所有工作都要重做。
